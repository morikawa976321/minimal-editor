# ネイティブ採用版とブラウザ版 · 2026-10-18

## 採用と非同期保存

本人の指示でネイティブ版を採用した。`Store`は専用の保存スレッドが所有し、保存・読込・作成・改名・保管・復元を画面とは別に実行する。画面側は結果を非同期で受け取り、通常の自動保存中も本文を入力できる。入力ごとに保存要求を無制限に積まず、処理中1件と画面に残る最新本文へまとめる。保存結果にはメモIDと世代を付け、古い完了通知で最新本文を保存済みにしない。

新規・切替・保管・終了は、その時点までの追加入力も保存してから進める。本文を実際に入れ替える短い処理中のみ編集欄を保護し、通常自動保存では読み取り専用にしない。IME変換中の終了は変換終了と最新保存を待つ。保存失敗時は画面の本文を保持し、切替・終了を取り消す。強制終了で保存待ちの入力が残ることまでは保証しない。バックアップ・履歴・外部変更検出・排他ロックは既存のStoreを維持する。

検証: workerへ1,000msの遅延を入れても、その間の追加入力と状態取得は遅延終了前に完了。古い保存通知が未保存の追記を消さないこと、切替待機中の追記、競合時の最新復元コピー、IME終了待ち、構造操作中の終了要求を確認。`.work/native-async-ui-tierm1br/result.json` の応答測定は0〜16ms（注入試験の単回観測、製品性能保証ではない）。通常の実GUIは `.work/native-next-ui-7_2dx4_g/result.json`、保持したブラウザ起動は `.work/edge-desktop-ytdtemru/result.json`。

## 開く

通常の **Win → minimal-editor → Enter** はネイティブ版を開く。リポジトリ直下の **`ネイティブ版.vbs`** でも開ける。ブラウザ版は **`ブラウザ版.vbs`**。**`ネイティブ比較.vbs`** の比較ページからも両方を開ける。

ネイティブ版だけなら **`ネイティブ版.vbs`**。初回の原稿コピーだけ短時間Nodeを使い、以後はexeへ直接渡す。エディター本体はRustの単独プロセスで動き、ブラウザ・常駐Nodeサーバーは必要ない。

比較ページ自体はEdgeと小さなローカルNode補助を使う。ページを閉じると補助は最後の通信から90〜100秒後に終了する。ネイティブ本体のメモリ測定にはこれらを含めず、測定対象を明示する。両画面や比較ページを開いたままのPC全体の消費量が、ネイティブ単体の値になるわけではない。

- ブラウザ版の本文・一覧は変更せず、明示起動を残す。日常の起動先のみネイティブ版へ切り替えた。

## 試用後の評価と技術差

2026-10-18の本人評価:

見た目と操作には問題がないという試用結果を受領した。結果ブロックの貼付は再要求しない。採用先の切替を指示した発言とは扱わず、以下の技術差を説明する。

### 両方式の技術差

| 項目 | ブラウザ版 | ネイティブ版 |
| --- | --- | --- |
| 実装 | HTML/CSS/JavaScript＋Node.js | Rust＋Win32 |
| 本文の入力部品 | EdgeのHTML textarea | Windows標準Rich Edit（Msftedit.dll） |
| 一覧等の表示 | HTML要素をCSSで配置・装飾 | RustからWindowsの描画APIを呼んで配置・描画 |
| 保存の経路 | 入力画面→PC内HTTP→Node→ファイル | 入力画面→同じexe内の別スレッド→ファイル |
| 常駐基盤 | Edgeの関連プロセス＋Node | ネイティブexe1個とWindowsの共有部品 |
| 外観変更 | CSSで字間・影等を指定しやすい | 標準部品の制約があり、未対応の描画は自作が必要 |
| 他OSへの移行 | Webの画面は再利用しやすい。起動・保存周辺は対応が必要 | 現実装はWindows専用。Win32とRich Editの部分を作り直す必要がある |

両方とも原稿はローカルのUTF-8プレーンテキスト。ブラウザ版のHTTPは127.0.0.1との通信で、原稿保存のためにインターネットへ接続する必要はない。ネイティブ版は編集・保存にブラウザエンジンや常駐Nodeを必要としないため、その基盤のメモリを省けた。OS標準のIME・選択・Undo等を使うので、それらをすべて自作したアプリでもない。

### 一行の文字数に差が出る理由

コードで確認できる差は、ブラウザ版の字間0.01em（20pxの本文に対し0.2px相当）が、Rich Edit側では描画されないこと。Microsoftの [CHARFORMAT2W](https://learn.microsoft.com/en-us/windows/win32/api/richedit/ns-richedit-charformat2w_1) もsSpacingは表示へ影響しないと説明している。計算上は50文字で約10pxの差になり、他条件が同じなら字間が少ない側に多くの文字が入る方向へ働く。この10pxは計算例であり、本人の画面で測った値ではない。

さらに、CSSのフォントフォールバックとRich Editのフォント関連付け、文字幅・行末禁則・折返しの処理が異なる。最大幅・余白の目標は揃えているが、実際の本文領域はウィンドウ寸法やDPIにも依存する。本人の比較を同じ本文・同じ実効幅で測定していないため、観測された文字数差の全量を字間だけのせいとは断定しない。両方の文書が異なる意味で保存されている、という差ではない。

### フォントの太さが違って見える理由

本人の追加質問（2026-10-18）:

> フォントの見た目、特に太さが変わったのだが、これはなぜ?

コード上、ブラウザ本文はfont shorthandのnormal（400相当）、20px。ネイティブはフォント名・サイズ等を指定するが、CFM_WEIGHTやCFM_BOLDを指定しておらず太さはRich Editの既定値を使っていた。ゼロ初期化されたweight欄が0だから極細になる、という意味ではない。指定マスクに含まれない欄は適用されない（[CHARFORMAT2W](https://learn.microsoft.com/en-us/windows/win32/api/richedit/ns-richedit-charformat2w_1)）。

推測だけで済ませず、既存build/native-next.exeを専用の非表示desktopで起動し、隔離データへ「abc日本語ABC」を入力。対象プロセス内に確保した116byteのCHARFORMAT2Wを使ってEM_GETCHARFORMATを読み出した。既定書式と英字・日本語の各選択範囲でweight 400・bold false・height 300twipsを確認。英字はIntel One Mono、日本語はBIZ UDゴシック（charset 128、CFE_FONTBOUND）だった。結果は `.work/native-font-7c568i48/result.json`、調査スクリプトは `.work/font_probe.py`。表示倍率は125%。本人の画面や実原稿に触れていない。

同じ400でも文字の輪郭をピクセルへ変換する方法、ピクセル位置への丸め、アンチエイリアスと濃度補正が違うと太さが違って見える。ブラウザはChromiumのDirectWrite/Skiaを組み合わせる描画経路、比較版はMsftedit.dllのRICHEDIT50W入力部品を使用する。Microsoftの [RichEditD2Dの解説](https://devblogs.microsoft.com/math-in-office/richeditd2d-window-controls/) は従来のGDI/UniscribeとD2D/DirectWriteの経路を区別している。また [Edgeの描画解説](https://blogs.windows.com/msedgedev/2025/01/30/better-text-contrast-for-all-chromium-based-browsers-on-windows/) も、描画経路とコントラスト・ガンマ補正が、特にCJK文字の濃さに影響することを説明している。古いChromiumの薄い描画が現在もそのまま残るという説明にはしない。

今回確認できたのは「ブラウザのCSS指定とネイティブの書式の太さはどちらも400で、ネイティブは太字になっていない」こと。描画の差が有力だが、本人が開いたブラウザの実使用フォント、拡大率、両画面の実ピクセルと補正値までは測っていないため、原因を一つへ断定しない。ネイティブで日本語のフォント関連付けが働くことは確認できたが、それだけでブラウザの各文字も同じ物理フォントファイルだとは確定しない。同じ名前とサイズを指定するだけでは外観一致の保証にならない。今回は理由を説明し、太さの調整や描画方式の変更は行わない。
