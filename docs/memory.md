# メモリ削減の調査 · 2026-10-18

続く本人依頼でネイティブ比較版を作成した。新しい版は専用RAM約4〜5MiB、共有込み約29〜30MiBを測定。開き方は [native-comparison.md](native-comparison.md)、新しい測定・10MBの構成比較は [native-memory-options.md](native-memory-options.md)。以下はその前に行った既存試作の調査記録。

## 結論

現在のUIの規模なら、10MB前後を目指すために外観や操作を大幅に削る必要がある、とは判断しない。ダーク配色・余白・必要な時だけ出る一覧・ショートカット・自動保存はネイティブでも実装できる。ただし、現行版の全機能・文字組み・入力品質を揃えた完成版が10MBに収まることは未検証。

ブラウザとNodeの構成のままで全体10MBは今回の測定から支持できない。保存サーバーを含めてネイティブの単一プロセスにまとめる方向が候補になる。既存Bをそのまま採用する判断ではない。

## 実測

`tests/memory_desktop.py` で、表示を切り替えない専用Windows desktopに通常のネイティブ画面を作成。個人の原稿・稼働中サーバー・実用ブラウザプロファイルには接続していない。Nodeは既存のテスト用保存サーバーを使い、隔離した本文を読み込んだ待機状態。各条件3起動、準備完了後0.5秒間隔で3回、計9点を取得した。起動ピーク、長時間利用、入力・IME・Handy・多数メモ・Undo履歴増加時は測っていない。

単位はMiB（1,048,576 bytes）。以下の範囲は測定値の最小〜最大であり、合否の閾値ではない。

| 条件 | 専用RAM（private working set） | 共有ページ込みRAM（working set） | 専用コミット |
| --- | ---: | ---: | ---: |
| 既存Rust/標準EDIT試作、空本文 | 3.211–3.238 | 24.469–24.637 | 4.430–4.457 |
| 同試作、日本語等14,700字 | 3.586–3.629 | 25.289–25.473 | 4.859–4.918 |
| Node保存サーバーのみ、同じ本文 | 17.418–17.516 | 47.031–47.121 | 27.934–28.367 |

測定APIは [PROCESS_MEMORY_COUNTERS_EX2 / GetProcessMemoryInfo](https://learn.microsoft.com/en-us/windows/win32/api/psapi/ns-psapi-process_memory_counters_ex2)。専用コミットは物理RAM使用量とは異なる。共有ページ込みの値にはOS部品等も入り、他のプロセスと共有するページを含む。専用RAMだけを使って「アプリの全物理メモリが3.6MiB」とは表現しない。本人の観測した「100mb」の対象プロセス・指標は確認していないため、今回の値と同じ条件の削減率は出さない。

最終測定時の空きRAMは1.604GiB。AGENTS.mdの6GB未満では軽くする規則に従い、新たなブラウザは起動せず軽い2方式だけを直列測定した。ブラウザ版の総量や、HTML/CSSのどの部分が何MB使うかは今回測っていない。作業中にworking setを強制削減するAPIは使っていない。

生データ: `.work/memory-desktop-2sm583ry/result.json`（git対象外）。上表と再現スクリプトをGitに残す。通常のsandboxではCreateDesktopWが拒否されるため、隔離試験をsandbox外で実行した。親が専用jobを所有し、終了時には試験が作った子プロセスだけを終了する。

再現: uv管理の既存Python 3.12で `tests/memory_desktop.py` を実行する。既存 `build/native.exe` が必要。なければ `scripts/build.ps1` で構築する。Python自身と測定用親プロセスは製品のメモリ値に含まない。

## UIと入力に関する判断

現在のネイティブ試作は標準EDITで、現行の複数メモ・アーカイブ・取消UIを移植したものではない。本人は以前、B/Cの変換前の日本語が反転することを嫌だと述べている。専用RAMが小さいことだけで現行版を置換しない。

Windowsの [Rich Edit](https://learn.microsoft.com/en-us/windows/win32/controls/about-rich-edit-controls) はIME・文字/段落書式を持つので別の入力部品の候補になる。[書式API](https://learn.microsoft.com/en-us/windows/win32/controls/using-rich-edit-controls) が存在することは、ブラウザと同じ字形・折返し・行間1.8・字間0.01em・IME配色になる証明ではない。変更版のメモリも未測定。自前で文字入力全体を描画する案はIME・選択・Undo・アクセシビリティの実装負担が大きい。

**astra の判断**: 10MBを厳密な上限とするためにIMEや使い心地を削るのは推奨しない。まず現行の見た目と操作を保つネイティブ版の成立性を確認し、専用RAM・共有込みRAM・入力時のピークを分けて評価するのが妥当。ただし今回は調査の依頼であり、方式選択を覆す移植や実用ランチャーの切替は実施していない。
